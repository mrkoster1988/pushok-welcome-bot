# MAX webhook — 0.1.0-alpha.4

Реализованы приём HTTPS-событий через обратный прокси, проверка секрета, SQLite-очередь
и отдельный обработчик команд. Токен, настоящий домен и доставка в MAX ещё не проверены.
Локально проверены логика и HTTP через Gunicorn; сборку Docker и TLS нужно подтвердить на VPS.

## Что подготовить

- Отдельный бот MAX, добавленный в тестовый групповой чат, и его токен.
- Домен с DNS на VPS; доступный HTTPS на порту 443 и доверенный сертификат.
- Установленные Docker Engine / Compose и Caddy на хосте. Их установка этим примером не выполняется.
- Отдельный каталог установки и база для каждого бота. Не используйте один токен в нескольких проектах.

MAX принимает URL без явного порта. Здесь адрес имеет вид `https://bot.example.org/webhooks/max`.
Long Polling нужен только для тестов; одновременно с webhook его запускать нельзя.

## 1. Настройки

При новой установке скопируйте `.env.example` в `.env`, `groups.multi.example.json` в `groups.json`.
При обновлении сохраните свои файлы. В разделе `max` укажите числовой ID тестовой группы
и ID администраторов. Другие группы игнорируются. Права определяются списком `admins`.

Заполните `.env` на сервере:

```dotenv
BOT_PLATFORM=max
MAX_TOKEN=ваш_токен
MAX_WEBHOOK_SECRET=ваш_случайный_секрет
MAX_WEBHOOK_PORT=8080
DB_PATH=data/max.sqlite3
GROUPS_FILE=groups.json
```

Сгенерировать секрет можно командой ниже. Скопируйте результат только в `.env`, не в чат/GitHub.

```bash
python3 -c 'import secrets; print(secrets.token_urlsafe(32))'
chmod 600 .env
chmod 644 groups.json
```

Секрет должен содержать 32–256 символов `A-Z`, `a-z`, `0-9`, `_`, `-`.
Если используется `MAX_CA_FILE`, подключите PEM-файл read-only **к обоим сервисам**.
Не отключайте проверку TLS. Для следующего бота на том же VPS выберите другой свободный порт.

## 2. Переход с polling и запуск

При обновлении сначала остановите прежний MAX polling и сохраните базу вместе с конфигурацией
в защищённом месте. Укажите **тот же DB_PATH** и используйте тот же каталог и имя Compose-проекта:
так сохранится прежний том `bot-data`. Не выполняйте `down -v`. Telegram/VK не требуют этого перехода.

```bash
docker compose stop bot
docker compose -f compose.max-webhook.yaml build
docker compose -f compose.max-webhook.yaml run --rm --no-deps worker python max_webhook.py check
docker compose -f compose.max-webhook.yaml up -d
docker compose -f compose.max-webhook.yaml ps
curl --fail http://127.0.0.1:8080/healthz
```

Для новой установки команду `stop bot` пропустите. `check` проверяет только локальные настройки.
Worker при старте обращается к MAX, проверяет ID бота и привязку базы. Receiver ждёт готовности
worker. Файловая блокировка запрещает второй worker/polling с той же базой на одном сервере.
При другом MAX_WEBHOOK_PORT замените порт в curl и Caddyfile. База alpha.2 дополняется таблицами автоматически.

## 3. HTTPS и регистрация

Возьмите блок из `Caddyfile.max-webhook.example`, замените домен и порт, добавьте его в существующий
Caddyfile, проверьте конфигурацию и перезагрузите Caddy. Пример рассчитан на Caddy на хосте:
в контейнере адрес `127.0.0.1` указывает на сам контейнер и требует другой сетевой настройки.
Публично открыт только `/webhooks/max`; `/healthz` остаётся локальным.

Сначала проверьте TLS и маршрут **без секрета**:

```bash
curl -i -X POST -H 'Content-Type: application/json' --data '{}' https://bot.example.org/webhooks/max
```

Ожидается **403** от приложения, без ошибок сертификата. Только после этого зарегистрируйте подписку:

```bash
docker compose -f compose.max-webhook.yaml exec worker python max_webhook.py register --url https://bot.example.org/webhooks/max
```

Эта команда действительно меняет webhook-подписку в MAX. При подписке на чужой URL она остановится,
сохранив её. Повтор для того же URL обновляет секрет и тип событий. Приложение проверяет `success=true`.
Регистрация сама по себе не доказывает доставку: отправьте новую `/help` в разрешённый чат.

## 4. Проверка и наблюдение

```bash
docker compose -f compose.max-webhook.yaml exec worker python max_webhook.py status
docker compose -f compose.max-webhook.yaml logs --tail=50 worker receiver
```

| Поле/статус | Значение и действие |
|---|---|
| worker_alive | Обработчик оставлял отметку в последние 90 секунд; это не проверка доставки |
| inbox pending / done | Событие ожидает обработки / команда разобрана |
| inbox failed | Три ошибки обработки; требуется разбор базы, событие сохранено |
| outbox pending / sending | Ответ ждёт отправки / начата попытка отправки |
| outbox sent | API подтвердил отправку; проверьте сообщение в чате |
| outbox uncertain | Исход попытки неизвестен; проверьте чат перед ручными действиями |
| inbox/outbox held | Старая очередь после восстановления: удержана для ручного разбора |
| outbox cancelled | Чат удалён из разрешённых; отложенный ответ отменён |

Приёмка: `/help`, сценарий из `scenario.json`, отказ обычному участнику в админ-команде,
игнорирование постороннего чата, перезапуск и сохранность данных. Для применения изменения
groups.json перезапустите **оба сервиса**. Смена токена на другого бота с прежней базой блокируется.

## Поведение при сбоях и границы

HTTP 200 для подходящей команды возвращается после записи в SQLite. Повтор события не применяет
команду заново. Изменение данных, ID события и ответ сохраняются одной транзакцией; неотправленный
ответ переживает перезапуск. До обращения к API ответ переводится в `sending`: после обрыва связи
или перезапуска в этом состоянии он становится `uncertain`. Автоматического повтора такой попытки
нет, поскольку сообщение уже могло дойти. Гарантии доставки «ровно один раз» нет.

При недоступной базе или очереди в 10 000 необработанных событий/ожидающих ответов возвращается 503.
После трёх ошибок обработки событие получает `failed`, чтобы другие команды могли продолжиться.
Уже завершённые события и ответы остаются в базе: архивирование, очистка, автоматический backup,
админ-интерфейс повторов и ограничение частоты команд пока не реализованы. Следите за диском.
Один worker и локальная SQLite рассчитаны на начальный запуск; нагрузочная приёмка не проведена.

Приёмник получает события `message_created` и выполняет только текстовые команды в группах.
Публикация в каналы, личные диалоги MAX, автоприветствия и кнопки этим выпуском не добавлены.
Не отправляйте секреты в команды: текст ответа и состояние хранятся в базе, ответы видны группе.

Официальные источники: [MAX webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions),
[Gunicorn](https://gunicorn.org/quickstart/), [Caddy reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).
